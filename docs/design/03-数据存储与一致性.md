# 积乐圈 · PointJoy：数据存储与一致性设计 v0.1

状态：逻辑数据库设计和事务规范，尚未生成可执行迁移。配套：[交互设计](01-交互与业务设计.md)、[接口协议](02-接口协议.md)。

## 1. 存储职责

- PostgreSQL：身份关联、会话、群组、成员、申请、积分账户与流水、奖励库存、兑换订单、幂等及审计。
- COS：用户头像、群头像、奖励展示图。数据库存 assetId/objectKey，不以有时效的签名 URL 作为持久引用。
- Redis 第一版不依赖；余额和库存的正确性不依赖缓存或分布式锁。
- 单个 NestJS 应用按 Auth、Groups、Memberships、Points、Rewards、Redemptions、Assets 分模块；数据库连接统一管理，禁止领域模块绕开事务直接更新积分。

## 2. 类型和通用规则

ID 为 UUID，时间为 timestamptz，所有时间由服务端生成。账户/积分/库存使用 bigint，接口上限 2,000,000,000；Node 层显式处理 bigint 并在范围检查后转换为 JSON number。版本号使用 bigint 并执行同样边界检查。

除标注 `?` 的字段外均非空。业务表默认有 id、created_at；可变表另有 updated_at、version（初始 1）。表名 snake_case，API camelCase。status/type 用 text + CHECK 显式约束，便于迁移；删除行为 RESTRICT。JSONB 仅保存快照、受控审计差异和幂等结果，不存放核心关联关系。

所有群内表携带 group_id，并使用复合外键约束同群归属。服务端查询同时携带 group_id 和资源 id；数据库约束是额外保护，不替代授权。

## 3. 逻辑表结构

### users：平台用户

`id, display_name varchar(40), avatar_asset_id? FK assets, status ACTIVE|DISABLED, version, created_at, updated_at`。

昵称不唯一；账号禁用由未来平台操作处理，鉴权层预留状态检查。

### auth_identities：外部身份

`id, user_id FK users, provider WECHAT, app_id varchar(64), subject varchar(128), union_id? varchar(128), created_at`。

UNIQUE(provider, app_id, subject)。subject 保存 openid，union_id 可空，不据此在未验证时自动合并账号。

### auth_sessions：登录会话

`id, user_id FK users, refresh_hash bytea UNIQUE, expires_at, revoked_at?, last_used_at, created_at`。

accessToken 的 sid 指向会话。刷新使用 SELECT FOR UPDATE，更新 refresh_hash；另表 `used_refresh_tokens(session_id, token_hash UNIQUE, used_at, expires_at)` 记录已使用 token 哈希到过期，以识别重放并撤销会话。会话秘密不进入审计日志。

### groups：群组

`id, name varchar(30), description varchar(200), avatar_asset_id?, owner_member_id, version, created_at, updated_at`。

owner_member_id 非空，以 `(id, owner_member_id)` 延迟外键指向 members(group_id, id)。建群事务预生成群和成员 ID，先插群、再插成员、账户，提交时验证。不能把群主绑定到其他群。

### members：群内成员

`id, group_id FK groups, user_id FK users, role MEMBER|ADMIN, version, created_at, updated_at`。

UNIQUE(group_id, user_id)，UNIQUE(group_id, id)。OWNER 为成员 id 等于群 owner_member_id 时的派生角色，不存第三种角色值。Member API 包含 version，以支持角色编辑。

user_id 单独不唯一，users 与 groups 通过 members 构成多对多关系。同一用户可属于多个群，每个成员关系独立拥有角色和积分账户；群创建接口不设置“一人一群”限制。users、auth_sessions 不保存用于授权或业务路由的 current_group_id，最近选择仅作为客户端按用户隔离的导航偏好。

### invitations：邀请

`id, group_id, creator_member_id, token_hash bytea UNIQUE, code_hash bytea UNIQUE, expires_at, max_uses int, uses int DEFAULT 0, revoked_at?, created_at`。

CHECK(max_uses BETWEEN 1 AND 100 AND uses BETWEEN 0 AND max_uses)。复合外键 creator 指向同群成员。成功创建的新申请才增加 uses；邀请失效不删除。

### join_applications：入群申请

`id, group_id, invitation_id, applicant_user_id FK users, status PENDING|APPROVED|REJECTED|WITHDRAWN, decision_reason? varchar(200), decided_by_member_id?, decided_at?, created_at`。

同群邀请复合外键；处理人同群复合外键。部分唯一索引 `(group_id, applicant_user_id) WHERE status='PENDING'`。非 PENDING 必须有 decided_at；APPROVED/REJECTED 必须有处理人，WITHDRAWN 的处理人为空。审批与成员创建在同事务。

### point_accounts：积分账户

`id, group_id, member_id, balance bigint DEFAULT 0, version bigint DEFAULT 0, created_at, updated_at`。

UNIQUE(group_id, member_id)，成员复合外键；CHECK(balance BETWEEN 0 AND 2000000000 AND version>=0)。初始版本例外为 0，第一笔流水对应版本 1。

### point_ledger：积分流水，只追加

`id, group_id, member_id, type GRANT|ADJUSTMENT|REVERSAL|REDEEM|REFUND, delta bigint, balance_after bigint, account_version bigint, reason varchar(200), actor_member_id, order_id?, reversal_of_id?, created_at`。

- 同群 member/actor/order/reversal 复合外键；UNIQUE(group_id,id)。
- UNIQUE(group_id, member_id, account_version)，每次账户变更恰好递增一次 version。
- delta 非零，balance_after 在账户允许范围内，account_version >0。
- GRANT、REFUND 必须 delta>0，REDEEM 必须 delta<0。
- REDEEM/REFUND 必须有 order_id，其他类型 order_id 为空。
- REVERSAL 必须有 reversal_of_id，其他类型为空。
- 部分唯一索引 `(group_id, order_id, type) WHERE type IN ('REDEEM','REFUND')`，防止同一订单重复扣分/退款。
- 部分唯一索引 `(group_id, reversal_of_id) WHERE reversal_of_id IS NOT NULL`，防止二次冲正。
- 可增加复合外键 `(group_id, member_id, reversal_of_id)` 指向原流水相同列，确保冲正属于同账户。原始类型、相反金额由事务业务规则验证。
- 数据库应用角色禁止 UPDATE/DELETE 本表；纠错新增流水，迁移账号独立。

### rewards：奖励及可用库存

`id, group_id, name varchar(50), description varchar(2000), image_asset_id?, type VIRTUAL|PHYSICAL, fulfillment_mode MANUAL, fulfillment_instructions varchar(500), cost_points bigint, stock_available bigint, status DRAFT|ACTIVE|INACTIVE, version, stock_version bigint, created_at, updated_at`。

UNIQUE(group_id,id)。CHECK(cost_points BETWEEN 1 AND 2000000000)，CHECK(stock_available BETWEEN 0 AND 2000000000)。version 初始 1，stock_version 初始 0；类型及 fulfillment_mode 创建后不变。

version 只反映文案/价格/上下架；stock_version 只反映库存账变。商品价格改变不更新订单快照或旧流水。

### stock_ledger：库存流水，只追加

`id, group_id, reward_id, type INITIAL|ADJUSTMENT|REDEEM|RESTORE, delta bigint, stock_after bigint, stock_version bigint, order_id?, actor_member_id, reason varchar(200), created_at`。

奖励/操作者/订单均为同群复合外键；UNIQUE(group_id,reward_id,stock_version)。INITIAL 初始库存为 0 时不写流水；非零初始库存写版本 1。所有流水 delta 非零，stock_after 非负，REDEEM=-1，RESTORE=+1。REDEEM/RESTORE 才有 order_id。

部分唯一索引 `(group_id,order_id,type) WHERE type IN ('REDEEM','RESTORE')`；每个 reward 最多一条 INITIAL。人工减库存只减少可用量，不能减少已经被订单占用的数量。

取消时需要恢复一件，因此人工补货必须检查 `stock_available + PENDING订单数 <= 2000000000`，在奖励行锁内执行。这样库存数值上限不会阻塞合法取消退款。

### redemptions：兑换订单

`id, group_id, member_id, reward_id, status PENDING|FULFILLED|CANCELED, quantity int DEFAULT 1, cost_points bigint, reward_snapshot jsonb, version, fulfilled_at?, fulfilled_by_member_id?, fulfillment_method? TOKEN|MANUAL, fulfillment_note? varchar(200), canceled_at?, canceled_by_member_id?, cancel_reason? varchar(200), created_at, updated_at`。

- UNIQUE(group_id,id)，成员/奖励/各操作者同群复合外键，quantity=1，cost_points>0。
- reward_snapshot 保存 name、type、fulfillmentMode、fulfillmentInstructions、imageAssetId；API 解析图片 URL，快照不保存短效 URL。
- PENDING：完成/取消时间及操作者均空。
- FULFILLED：完成时间、操作者、方式非空，取消字段为空。
- CANCELED：取消时间、操作者、原因非空，完成字段为空。
- JSONB 快照的必要字段、类型和长度在 DTO 与领域层验证。关联图像在订单保留期间不能删除。

### redemption_claims：短时核销凭据

`id, group_id, order_id, generation bigint, token_hash bytea UNIQUE, manual_code_hash bytea, expires_at, revoked_at?, created_at`。

同群订单外键；UNIQUE(group_id,order_id,generation)，manual_code_hash 在群内唯一。生成随机码遇碰撞重试。订单锁内撤销旧代并插新代。核销先锁订单，再确认凭据仍有效；不通过一次扫码预览永久授予核销权限。

### assets：图片元数据

`id, uploader_user_id, group_id?, purpose AVATAR|GROUP_AVATAR|REWARD_IMAGE, object_key UNIQUE, content_type, size_bytes, status PENDING|READY|REJECTED, created_at, ready_at?`。

AVATAR 群为空；群图/奖励图群非空。引用时检查 uploader 或群权限与用途。COS 完成检查不在积分事务内执行。无引用的 PENDING 对象可在 24 小时后清理，READY 对象先检查包括历史快照在内的引用。

### idempotency_records：幂等请求

`id, user_id, operation_scope varchar(300), key UUID, request_hash bytea, http_status int, response_ciphertext bytea, encryption_key_version int, created_at`。

UNIQUE(user_id, operation_scope, key)。响应加密保存以兼容邀请和核销秘密，不含 requestId；重放生成当前 requestId。初始占位和完成结果在同一事务，其他事务不应看见已提交的占位状态；实现可允许事务内暂时 NULL，提交前应用强制填完整，迁移阶段可补延迟约束触发器。

首版不删除成功幂等记录。数据库临时事务重试继续用同键，不能换键绕过冲突。

### audit_logs：管理操作，只追加

`id, group_id, actor_member_id, action, target_type, target_id UUID, reason?, changes jsonb, request_id UUID, created_at`。

群内 actor 外键；target 多态关联由服务端验证。记录发分、调整、冲正、角色变化、群主转让、审批、奖励编辑、库存调整、取消、核销。changes 使用允许字段清单，禁止记录 token、refreshToken、openid、完整请求头。与对应写操作同事务提交。

## 4. 索引

| 查询 | 索引 |
|---|---|
| 我的群组 | members(user_id, created_at DESC, id DESC) |
| 管理成员 | members(group_id, created_at DESC, id DESC) |
| 本人积分明细 | point_ledger(group_id, member_id, created_at DESC, id DESC) |
| 奖励列表 | rewards(group_id, status, created_at DESC, id DESC) |
| 本人订单 | redemptions(group_id, member_id, created_at DESC, id DESC) |
| 管理待领取订单 | redemptions(group_id, status, created_at DESC, id DESC) |
| 待加入申请 | join_applications(group_id, status, created_at DESC, id DESC) |
| 本人申请 | join_applications(applicant_user_id, created_at DESC, id DESC) |
| 库存明细 | stock_ledger(group_id, reward_id, created_at DESC, id DESC) |

外键引用列按查询补索引，避免盲目为每个字段建索引。第一版成员昵称搜索在本群过滤后执行，规模增长再按真实查询计划增加检索索引。

## 5. 锁和授权顺序

采用 READ COMMITTED + 显式行锁与条件校验。每个群内写事务先取得幂等键，再对 groups 行 FOR SHARE，随后读取当前成员角色并检查权限。角色修改和群主转让使用 groups 行 FOR UPDATE，阻止与旧权限写事务穿插；这些动作不得先取得 SHARE 再升级锁。

统一业务锁顺序：群 → 订单（涉及已有订单时）→ 奖励 → 原始积分流水（冲正时）→ 积分账户。同类多行按 UUID 排序。申请流程采用群 → 邀请 → 申请；审批只锁申请，不反向再锁邀请。核销凭据在订单之后锁。所有流程遵守子集顺序。

群 SHARE 允许不同成员正常业务并发；只有权限/所有权变化要求独占群锁。读接口按当前已提交权限授权，后续角色变化不撤回已经返回的读取结果。

## 6. 事务规范

### 6.1 创建群

生成群、成员 ID → 创建幂等占位 → 插群（预填 owner_member_id）→ 插成员 → 插零余额账户 → 写成功响应 → 提交。循环外键延迟到提交校验。

### 6.2 发分、调整、冲正

幂等 → 群锁与实时权限 → 冲正时锁原记录 → 锁目标账户 → 检查非本人、原流水可冲正、金额与余额边界 → 更新 balance、version → 插流水 → 插审计 → 保存响应 → 提交。

积分 delta 由服务端验证，冲正 delta=-原 delta。普通变更与冲正始终在同一账户锁下计算 balance_after，不从前端余额推算。

### 6.3 创建兑换

1. 幂等占位，群 SHARE 锁，检查有效成员。
2. 奖励 FOR UPDATE，检查属于本群、ACTIVE、version 和 costPoints 与用户确认值相符、stock_available>=1。
3. 本人账户 FOR UPDATE，检查 balance>=服务端奖励价格。
4. 生成订单 ID，写 PENDING 订单和完整奖励快照。
5. 扣账户余额、递增账户 version；写 REDEEM 积分流水。
6. 可用库存减 1，递增 stock_version；写 REDEEM 库存流水。
7. 保存幂等成功响应并提交。任一步失败全部回滚。

数据库事务内不请求 COS、微信或其他外部服务。若以后需要通知，用同事务 outbox 表交给后台工作器发送，通知失败不能撤销兑换。

### 6.4 取消兑换

幂等 → 群 SHARE 与权限 → 订单 FOR UPDATE → 检查本人/管理者与状态 → 奖励 FOR UPDATE → 账户 FOR UPDATE → 余额增加原订单 cost_points → 写 REFUND → 库存增加 1 并写 RESTORE → 订单变 CANCELED，撤销核销码 → 审计及幂等结果 → 提交。

允许返分不能突破余额上限：所有正向人工发分、减少积分的冲正，需检查 `当前余额 + 所有PENDING订单可退款积分 + 本次正向delta <= 2000000000`，在账户锁下计算；创建订单和退款保持这个总和不变，核销只降低潜在退款额。这样普通发分不能挤占待领取订单的退款空间。

已 CANCELED 时返回当前订单和账户，不重复写流水；已 FULFILLED 返回 INVALID_STATE。

### 6.5 核销

幂等 → 群 SHARE 与管理权限 → 订单 FOR UPDATE → 检查操作者不是订单成员 → 检查 PENDING → TOKEN 模式验证当前代/有效期/同群同订单，MANUAL 模式验证交付备注 → 更新 FULFILLED → 撤销凭据 → 审计及响应 → 提交。

核销不再扣分或扣库存。重复同键返回原结果；不同键对已完成订单返回当前订单，不重复交付记录。与取消竞争由订单锁串行决定。

### 6.6 入群申请与审批

提交申请：幂等 → 群 SHARE → 邀请 FOR UPDATE → 若已成员则返回冲突并引导进群；已有待审批申请则返回原申请 → 检查邀请有效性和名额 → 新增申请、uses+1 → 提交。

审批：幂等 → 群 SHARE 与管理权限 → 申请 FOR UPDATE → APPROVE 时插成员和零余额账户、更新申请；REJECT 仅更新申请 → 审计 → 提交。成员唯一约束兜底；如果其他合法路径已创建成员，复用成员并将申请标为 APPROVED。

### 6.7 奖励库存与编辑

编辑/上下架：群 SHARE 与权限 → 奖励 FOR UPDATE → 检查 expectedVersion → 修改内容、version+1。库存调整：同样锁奖励，校验 expectedStockVersion、delta、可用库存和潜在归还空间 → 更新库存及版本 → 库存流水和审计 → 提交。

## 7. 对账、恢复与运行约束

在同一个 REPEATABLE READ 只读快照内每日检查，避免跨查询瞬间变化导致误报：

- 每个账户 balance = SUM(point_ledger.delta)，账户 version = 最新流水 account_version。
- 每条积分流水的 balance_after 与按 account_version 累加结果一致。
- 每个奖励 stock_available = SUM(stock_ledger.delta)，库存版本与最新流水一致。
- 每笔订单恰有一条 REDEEM 积分流水和一条 REDEEM 库存流水，金额/数量与订单一致。
- CANCELED 订单恰有一条 REFUND 和一条 RESTORE；其他订单两者皆无。
- 每个成员有且只有一个账户；每个群主属于本群。

异常生成告警和待查记录，不静默重写账目。后端结构化日志携带 requestId、groupId、资源 ID 和耗时，记录死锁重试及失败率。迁移账号与应用账号分离，流水和审计表应用账号只读/插入。

开发与生产数据库及 COS 分环境。生产采用托管 PostgreSQL，启用自动备份和可用的时间点恢复；建议目标 RPO≤15分钟、RTO≤4小时，这只是目标，需根据购买配置及恢复演练验证。上线前至少在隔离库做一次恢复演练。

Prisma schema 不能完整表达的部分唯一索引、延迟复合外键和权限通过受版本管理的 SQL migration 落地；不能把 `db push` 当作生产变更流程。集成测试使用真实 PostgreSQL，覆盖并发兑换、撤销竞争、事务回滚、越权和幂等重放。

## 8. 参考与实现核验

以上业务模型是针对 PointJoy 的设计决策，并非官方预设方案。

- [PostgreSQL 约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html)：外键与唯一约束用于数据库层结构校验，跨表业务规则不能直接交给普通 CHECK。
- [PostgreSQL 显式锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)：实现时按本文锁顺序验证并发行为和死锁恢复。
- [Prisma 事务文档](https://www.prisma.io/docs/orm/reference/transactions-and-runtime)：锁定项目实际依赖版本后实现事务 API，本文不绑定尚未安装的具体版本调用语法。
